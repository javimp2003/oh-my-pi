Track acceptance requirements with executable checks against specific workspace file revisions.
For complex behavior changes, define the contract before implementation: one stable id, requirement, exact bash command, and relevant source/test file paths per check. Use commands from the project; cover the requested edge cases. Keep checks proportionate; one command may establish several requirements.
Run checks with bash after implementing. Status is computed from actual completed commands, never from a model claim. A failed, cancelled, background-running or stale execution cannot pass. Commands run from the workspace root unless the check declares an optional relative `cwd`; other directories cannot certify it. Keep commands exact; use foreground checks. Changing a tracked file invalidates its evidence.
Within a user request, existing checks cannot be removed or weakened. A new user request starts a new contract. Status survives compaction and resume on the same branch. If a check cannot run, report the blocker accurately; never manufacture evidence.

`review` runs a fresh independent verifier on the current workspace after all declared checks pass. It executes focused tests and adversarial cases, and its verdict is audited against real child tool receipts. It does not inherit your conversation or repair files. Inspect reproduced findings, repair the failure and rerun affected checks before a second review. Two attempts per user request; cancellation consumes an attempt. Report blockers when checks/review cannot finish. Do not call a blocked review clean.

`status` also returns the latest independent review and its attempt count. An unchanged clean/issues review is reused by `review` without another model request. After repairing a reported failure, rerun the acceptance commands: new passing execution evidence allows the second review even for environment-only fixes. Changed requests, discarded branches or newer failed checks cannot inherit an earlier clean verdict.
